## Где лежат логи в Linux

Логи в Linux обычно находятся в двух основных местах:

1. В файлах, чаще всего в директории:

```
/var/log
```

2. В systemd journal, который читается через:

```
journalctl
```

На современных Linux-системах часто используются оба подхода одновременно.

---

# `/var/log`

`/var/log` — основная директория для логов системы и приложений.

Посмотреть содержимое:

```
ls -lah /var/log
```

Примеры файлов и директорий:

```
/var/log/syslog
/var/log/auth.log
/var/log/kern.log
/var/log/nginx/
/var/log/apache2/
/var/log/mysql/
/var/log/messages
/var/log/secure
```

Важно: набор файлов зависит от дистрибутива.

На Debian/Ubuntu часто:

```
/var/log/syslog
/var/log/auth.log
/var/log/kern.log
```

На RHEL/CentOS/Rocky/Alma часто:

```
/var/log/messages
/var/log/secure
```

---

# `journalctl`

`journalctl` — команда для чтения логов systemd-journald.

systemd-journald собирает логи:

- systemd-сервисов;
- ядра;
- boot-процесса;
- stdout/stderr сервисов;
- системных событий.

Посмотреть все логи:

```
journalctl
```

Смотреть логи с конца:

```
journalctl -e
```

Смотреть логи в реальном времени:

```
journalctl -f
```

Смотреть логи конкретного сервиса:

```
journalctl -u nginx
```

Смотреть логи сервиса в реальном времени:

```
journalctl -u nginx -f
```

Смотреть логи с определённого времени:

```
journalctl --since "2026-07-05 10:00"
```

За последний час:

```
journalctl --since "1 hour ago"
```

За сегодня:

```
journalctl --since today
```

Логи предыдущей загрузки:

```
journalctl -b -1
```

Логи текущей загрузки:

```
journalctl -b
```

Список загрузок:

```
journalctl --list-boots
```

---

# Где физически лежат логи journalctl

Если включено постоянное хранение:

```
/var/log/journal
```

Если постоянное хранение не включено, journal может храниться временно:

```
/run/log/journal
```

`/run` очищается после перезагрузки, поэтому такие логи могут пропасть.

Проверить настройки journald:

```
cat /etc/systemd/journald.conf
```

Важный параметр:

```
Storage=persistent
```

# `dmesg`

`dmesg` показывает сообщения ядра из kernel ring buffer.

Это полезно для диагностики:

- проблем с дисками;
- сетевыми картами;
- драйверами;
- OOM Killer;
- USB-устройствами;
- файловыми системами;
- kernel panic;
- hardware errors.

Пример:

```
dmesg
```

Читать удобнее:

```
dmesg -T
```

`-T` показывает человекочитаемое время.

Смотреть ошибки:

```
dmesg -T | grep -i error
```

Искать OOM Killer:

```
dmesg -T | grep -i oom
```

Пример:

```
dmesg -T | grep -i "killed process"
```

`dmesg` — это не совсем обычный лог-файл. Это вывод сообщений ядра из буфера.

# `syslog`

`syslog` — это общий системный лог.

На Debian/Ubuntu он обычно находится здесь:

```
/var/log/syslog
```

Там можно увидеть события от разных системных компонентов:

- cron;
- systemd;
- network;
- kernel;
- sudo;
- сервисы;
- демоны.

Пример просмотра:

```
less /var/log/syslog
```

Смотреть последние строки:

```
tail -n 100 /var/log/syslog
```

В реальном времени:

```
tail -f /var/log/syslog
```

Искать ошибки:

```
grep -i error /var/log/syslog
```

# `auth.log`

`auth.log` — лог авторизации и аутентификации.

На Debian/Ubuntu:

```
/var/log/auth.log
```

Там можно найти:

- SSH-логины;
- неудачные попытки входа;
- sudo-команды;
- смену пользователя через `su`;
- события PAM;
- блокировки аккаунтов.

Примеры:

```
less /var/log/auth.log
```

Найти SSH-логины:

```
grep sshd /var/log/auth.log
```

Найти успешные входы:

```
grep "Accepted" /var/log/auth.log
```

Найти неудачные входы:

```
grep "Failed password" /var/log/auth.log
```

Найти sudo-команды:

```
grep sudo /var/log/auth.log
```

На RHEL/CentOS/Rocky/Alma аналогичный лог часто лежит здесь:

```
/var/log/secure
```

# `kern.log`

`kern.log` — лог сообщений ядра.

На Debian/Ubuntu:

```
/var/log/kern.log
```

Там можно найти:

- kernel messages;
- hardware errors;
- network driver errors;
- disk errors;
- OOM Killer;
- filesystem errors.

Пример:

```
less /var/log/kern.log
```

Искать OOM:

```
grep -i oom /var/log/kern.log
```

Искать проблемы с диском:

```
grep -i "error" /var/log/kern.log
```

# `messages`

`/var/log/messages` — общий системный лог, часто используется в RHEL-based системах.

Примеры дистрибутивов:

- CentOS;
- RHEL;
- Rocky Linux;
- AlmaLinux;
- Fedora.

Путь:

```
/var/log/messages
```

Пример:

```
less /var/log/messages
```

Смотреть в реальном времени:

```
tail -f /var/log/messages
```

Искать ошибки:

```
grep -i error /var/log/messages
```

На Ubuntu вместо `/var/log/messages` чаще используется:

```
/var/log/syslog
```

# Логи nginx

Обычно логи nginx лежат здесь:

```
/var/log/nginx/
```

Основные файлы:

```
/var/log/nginx/access.log
/var/log/nginx/error.log
```

`access.log` — все HTTP-запросы.

Пример строки:

```
192.168.1.10 - - [05/Jul/2026:12:00:01 +0000] "GET /api/users HTTP/1.1" 200 512
```

Там видно:

- IP клиента;
- время запроса;
- HTTP-метод;
- URL;
- HTTP-статус;
- размер ответа;
- user-agent, если настроен.

Смотреть последние запросы:

```
tail -f /var/log/nginx/access.log
```

Найти 500 ошибки:

```
grep " 500 " /var/log/nginx/access.log
```

Найти 404 ошибки:

```
grep " 404 " /var/log/nginx/access.log
```

`error.log` — ошибки nginx.

Пример:

```
tail -f /var/log/nginx/error.log
```

Там можно найти:

- ошибки upstream;
- проблемы с конфигом;
- permission denied;
- connection refused;
- timeout;
- too many open files.

Пример поиска:

```
grep -i error /var/log/nginx/error.log
```

# Логи systemd-сервисов

Если сервис запущен через systemd, его логи обычно смотрят через `journalctl`.

Например, nginx:

```
journalctl -u nginx
```

Docker:

```
journalctl -u docker
```

PostgreSQL:

```
journalctl -u postgresql
```

Смотреть с конца:

```
journalctl -u nginx -e
```

Смотреть в реальном времени:

```
journalctl -u nginx -f
```

Смотреть только за сегодня:

```
journalctl -u nginx --since today
```

Смотреть за конкретный промежуток:

```
journalctl -u nginx --since "2026-07-05 10:00" --until "2026-07-05 11:00"
```

Смотреть ошибки:

```
journalctl -u nginx -p err
```

Уровни логов:

```
emerg
alert
crit
err
warning
notice
info
debug
```

Пример:

```
journalctl -p err
```

Покажет ошибки уровня `err` и выше.

# `tail -f`

`tail` показывает конец файла.

Последние 50 строк:

```
tail -n 50 /var/log/syslog
```

`tail -f` следит за файлом в реальном времени:

```
tail -f /var/log/syslog
```

Полезно, когда ты воспроизводишь проблему и сразу смотришь, что появляется в логах.

Например:

```
tail -f /var/log/nginx/error.log
```

После этого в другом терминале делаешь запрос:

```
curl http://localhost
```

И смотришь, появилась ли ошибка.

# `grep`

`grep` ищет текст в логах.

Искать слово `error`:

```
grep error /var/log/syslog
```

Без учёта регистра:

```
grep -i error /var/log/syslog
```

Искать несколько вариантов:

```
grep -Ei "error|failed|denied|timeout" /var/log/syslog
```

Показать строки вокруг найденной:

```
grep -C 3 "error" /var/log/syslog
```

`-C 3` — показать 3 строки до и 3 строки после.

Только строки после совпадения:

```
grep -A 5 "error" /var/log/syslog
```

Только строки до совпадения:

```
grep -B 5 "error" /var/log/syslog
```

Искать по всем логам в директории:

```
grep -Ri "permission denied" /var/log/
```

---

# `less`

`less` — удобная команда для чтения больших логов.

Открыть лог:

```
less /var/log/syslog
```

Полезные клавиши внутри `less`:

```
/текст     поиск вперёд
?текст     поиск назад
n          следующее совпадение
N          предыдущее совпадение
G          в конец файла
g          в начало файла
q          выйти
```

Открыть лог и перейти в конец:

```
less +G /var/log/syslog
```

Это удобно, если лог большой.

# `zgrep`

Старые логи часто сжаты в `.gz`.

Например:

```
/var/log/syslog.1
/var/log/syslog.2.gz
/var/log/syslog.3.gz
```

Обычный `grep` по `.gz` неудобен. Для этого есть `zgrep`.

Пример:

```
zgrep -i error /var/log/syslog.2.gz
```

Искать SSH-ошибки в старых auth-логах:

```
zgrep "Failed password" /var/log/auth.log.*.gz
```

Искать падение сервиса в старых логах:

```
zgrep -i "segfault" /var/log/syslog.*.gz
```

# Log rotation

Log rotation — это механизм ротации логов.

Проблема: если логи не ротировать, они будут бесконечно расти и могут забить диск.

Например, было:

```
/var/log/nginx/access.log
```

После ротации может стать:

```
/var/log/nginx/access.log
/var/log/nginx/access.log.1
/var/log/nginx/access.log.2.gz
/var/log/nginx/access.log.3.gz
```

То есть текущий лог остаётся в `access.log`, старый переименовывается, ещё более старые сжимаются.

Ротация может быть:

- daily;
- weekly;
- monthly;
- по размеру файла;
- с хранением определённого количества старых файлов.

---

# `logrotate`

`logrotate` — стандартная утилита для ротации логов.

Основной конфиг:

```
/etc/logrotate.conf
```

Дополнительные конфиги:

```
/etc/logrotate.d/
```

Например:

```
ls /etc/logrotate.d/
```

Там могут быть файлы:

```
nginx
apache2
rsyslog
docker
postgresql-common
```

Пример конфига logrotate:

```
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
    copytruncate
}
```

Что это значит:

```
daily       ротировать каждый день
rotate 7    хранить 7 старых логов
compress    сжимать старые логи
missingok   не ругаться, если файла нет
notifempty  не ротировать пустой лог
copytruncate скопировать лог и очистить старый файл
```

Проверить logrotate вручную:

```
sudo logrotate -d /etc/logrotate.conf
```

`-d` — debug mode, ничего реально не меняет.

Принудительно запустить:

```
sudo logrotate -f /etc/logrotate.conf
```

# Как найти ошибку в логах

Обычно алгоритм такой:

## 1. Понять, какой сервис сломался

Например:

```
systemctl status nginx
```

## 2. Посмотреть логи сервиса

```
journalctl -u nginx -e
```

Или в реальном времени:

```
journalctl -u nginx -f
```

## 3. Посмотреть application logs

Для nginx:

```
less /var/log/nginx/error.log
```

Для приложения:

```
less /var/log/myapp/app.log
```

## 4. Искать типовые слова

```
grep -Ei "error|failed|fatal|panic|exception|denied|timeout|refused|killed|oom" /var/log/syslog
```

## 5. Смотреть время вокруг ошибки

```
grep -C 5 "error" /var/log/syslog
```

## 6. Проверить системные проблемы

Например, OOM Killer:

```
dmesg -T | grep -i oom
```

Проблемы с диском:

```
dmesg -T | grep -Ei "error|fail|ext4|xfs|nvme|sda"
```

Проблемы с авторизацией:

```
grep -i "failed" /var/log/auth.log
```

# Как читать логи по времени

Через `journalctl` это удобнее всего.

С определённого времени:

```
journalctl --since "2026-07-05 10:00"
```

До определённого времени:

```
journalctl --until "2026-07-05 11:00"
```

За промежуток:

```
journalctl --since "2026-07-05 10:00" --until "2026-07-05 11:00"
```

Для конкретного сервиса:

```
journalctl -u nginx --since "2026-07-05 10:00" --until "2026-07-05 11:00"
```

За последние 10 минут:

```
journalctl --since "10 minutes ago"
```

Через обычные файлы логов нужно ориентироваться по timestamp в строках.

Например:

```
grep "Jul  5 10:" /var/log/syslog
```

Или для nginx:

```
grep "05/Jul/2026:10:" /var/log/nginx/access.log
```

# Как понять, почему сервис упал

Базовый алгоритм:

## 1. Проверить статус

```
systemctl status myapp
```

Там важно смотреть:

```
Active:
Main PID:
Exit code:
Status:
```

Пример:

```
Active: failed
Result: exit-code
ExecStart=...
code=exited, status=1/FAILURE
```

Это значит: процесс завершился с ошибкой.

## 2. Посмотреть логи сервиса

```
journalctl -u myapp -e
```

Или:

```
journalctl -u myapp --since "30 minutes ago"
```

## 3. Посмотреть, не убил ли его OOM Killer

```
dmesg -T | grep -i oom
```

Или:

```
journalctl -k | grep -i oom
```

`journalctl -k` показывает kernel logs.

## 4. Проверить, не занят ли порт

Например, сервис должен слушать порт 8080:

```
ss -lntp | grep 8080
```

Если порт уже занят, сервис может не стартовать.

## 5. Проверить права

Типовая ошибка:

```
permission denied
```

Ищем:

```
journalctl -u myapp | grep -i "permission denied"
```

Проверяем владельца файлов:

```
ls -lah /path/to/app
```

## 6. Проверить конфиг

Например, для nginx:

```
nginx -t
```

Для sshd:

```
sshd -t
```

Для systemd unit:

```
systemctl cat myapp
```

## 7. Проверить зависимости

Например, приложение не может подключиться к БД:

```
connection refused
timeout
no route to host
authentication failed
```

Тогда проверяем:

```
ss -lntp
ping
curl
nc -vz host port
```

# Application logs vs system logs

Важно отличать application logs от system logs.

## System logs

System logs — это логи самой системы и инфраструктурных компонентов.

Примеры:

```
/var/log/syslog
/var/log/messages
/var/log/auth.log
/var/log/kern.log
journalctl
dmesg
```

Там обычно находятся события:

- загрузка системы;
- systemd;
- kernel;
- sudo;
- SSH;
- cron;
- network;
- hardware;
- OOM Killer.

Пример system log:

```
kernel: Out of memory: Killed process 1234
```

Это не ошибка приложения напрямую. Это система убила процесс из-за нехватки памяти.

## Application logs

Application logs — это логи конкретного приложения.

Примеры:

```
/var/log/nginx/access.log
/var/log/nginx/error.log
/var/log/myapp/app.log
/var/log/postgresql/postgresql.log
/var/log/mysql/error.log
```

Там обычно находятся:

- ошибки приложения;
- HTTP-запросы;
- stack trace;
- exceptions;
- database errors;
- business events;
- application debug info.

Пример application log:

```
ERROR Failed to connect to database
```

Это уже ошибка на уровне приложения.

# Пример диагностики: nginx не стартует

Проверяем статус:

```
systemctl status nginx
```

Смотрим логи:

```
journalctl -u nginx -e
```

Проверяем конфиг:

```
nginx -t
```

Смотрим error.log:

```
tail -n 100 /var/log/nginx/error.log
```

Проверяем, не занят ли порт 80:

```
ss -lntp | grep ':80'
```

Типовые причины:

```
конфиг nginx сломан
порт уже занят
нет прав на файл сертификата
нет директории для логов
ошибка в upstream
```

# Пример диагностики: приложение упало

Проверяем сервис:

```
systemctl status myapp
```

Смотрим логи:

```
journalctl -u myapp --since "1 hour ago"
```

Ищем ошибки:

```
journalctl -u myapp --since "1 hour ago" | grep -Ei "error|fatal|panic|exception|failed"
```

Проверяем OOM:

```
dmesg -T | grep -i oom
```

Проверяем порт:

```
ss -lntp | grep 8080
```

Проверяем диск:

```
df -h
```

Проверяем inode:

```
df -i
```

Проверяем права:

```
ls -lah /path/to/app
```
