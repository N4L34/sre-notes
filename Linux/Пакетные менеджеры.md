# 11. Пакетные менеджеры

Пакетный менеджер — это инструмент, который устанавливает, обновляет и удаляет программы в Linux.

Он решает задачи:

- скачать пакет из репозитория;
- проверить подпись пакета;
- установить зависимости;
- обновить пакет;
- удалить пакет;
- показать, из какого пакета появился файл.

Примеры:

```
apt     # Debian/Ubuntu
dpkg    # низкоуровневый менеджер .deb пакетов

dnf     # RHEL/Fedora/Rocky/Alma/CentOS Stream
yum     # старый менеджер RHEL/CentOS
rpm     # низкоуровневый менеджер .rpm пакетов
```

---

# `apt`

`apt` — основной пакетный менеджер в Debian/Ubuntu.

Пример:

```
sudo apt install nginx
```

`apt` работает не напрямую с отдельным `.deb` файлом, а с репозиториями.

То есть обычно ты говоришь:

```
установи nginx
```

А `apt` сам:

1. смотрит в список репозиториев;
2. находит пакет `nginx`;
3. проверяет подписи;
4. скачивает пакет;
5. скачивает зависимости;
6. устанавливает всё через `dpkg`.

---

# `apt update`

```
sudo apt update
```

Важно: `apt update` **не обновляет программы**.

Он только обновляет локальный список доступных пакетов.

То есть система спрашивает у репозиториев:

> Какие версии пакетов сейчас доступны?

Пример:

```
sudo apt update
```

После этого система знает, что появились новые версии `nginx`, `openssl`, `curl` и так далее.

---

# `apt upgrade`

```
sudo apt upgrade
```

`apt upgrade` обновляет уже установленные пакеты до новых версий.

Обычно порядок такой:

```
sudo apt update
sudo apt upgrade
```

То есть сначала обновляем список пакетов, потом обновляем сами пакеты.

---

# Разница `apt update` и `apt upgrade`

```
sudo apt update
```

Обновляет **информацию о пакетах**.

```
sudo apt upgrade
```

Обновляет **сами установленные пакеты**.

Простая аналогия:

```
apt update  = посмотреть, какие обновления есть
apt upgrade = установить эти обновления
```

# `apt install`

Установить пакет:

```
sudo apt install nginx
```

Установить несколько пакетов:

```
sudo apt install nginx curl htop
```

Установить конкретную версию:

```
sudo apt install nginx=1.24.0-2ubuntu7
```

Посмотреть доступные версии:

```
apt list -a nginx
```

или:

```
apt-cache policy nginx
```

---

# `apt remove`

Удалить пакет:

```
sudo apt remove nginx
```

Но конфиги обычно остаются.

Например, после удаления `nginx` могут остаться файлы:

```
/etc/nginx/nginx.conf/etc/nginx/sites-enabled/
```

Чтобы удалить пакет вместе с конфигами:

```
sudo apt purge nginx
```

Удалить ненужные зависимости:

```
sudo apt autoremove
```

Типичный порядок полного удаления:

```
sudo apt remove nginx
sudo apt autoremove
```

Или жёстче:

```
sudo apt purge nginx
sudo apt autoremove
```

# `dpkg`

`dpkg` — низкоуровневый менеджер `.deb` пакетов.

`apt` использует `dpkg` под капотом.

Установить локальный `.deb` файл:

```
sudo dpkg -i package.deb
```

Но `dpkg` сам плохо решает зависимости.

Например:

```
sudo dpkg -i app.deb
```

Может выдать ошибку:

```
dependency problems prevent configuration of app
```

Тогда чинят зависимости так:

```
sudo apt install -f
```

Полезные команды `dpkg`:

```
dpkg -l
```

Показать установленные пакеты.

```
dpkg -l | grep nginx
```

Найти установленный пакет по имени.

```
dpkg -S /usr/sbin/nginx
```

Показать, из какого пакета появился файл.

```
dpkg -L nginx
```

Показать, какие файлы установил пакет.

# Репозитории `apt`

Репозиторий — это сервер, где лежат пакеты.

`apt` берёт пакеты из списка репозиториев.

Основные места:

```
/etc/apt/sources.list/etc/apt/sources.list.d/
```

Пример файла:

```
cat /etc/apt/sources.list
```

Пример записи репозитория:

```
deb http://archive.ubuntu.com/ubuntu noble main restricted universe multiverse
```

Грубо:

```
deb        — тип репозитория
URL        — адрес репозитория
noble      — версия Ubuntu
main       — секция пакетов
restricted — секция пакетов
universe   — секция пакетов
multiverse — секция пакетов
```

# GPG keys

GPG keys нужны, чтобы проверять, что пакеты действительно пришли из доверенного репозитория и не были подменены.

Схема такая:

1. Репозиторий подписывает метаданные своим ключом.
2. Сервер хранит публичный ключ репозитория.
3. `apt update` проверяет подпись.
4. Если подпись не совпадает — пакет считается недоверенным.

Ошибка может выглядеть так:

```
The following signatures couldn't be verified
NO_PUBKEY ...
```

В современных системах ключи часто кладут сюда:

```
/etc/apt/keyrings/
```

А репозиторий указывают через `signed-by`.

Пример:

```
deb [signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu noble stable
```

Важно: старый способ через `apt-key` считается устаревшим.

# `yum`

`yum` — старый пакетный менеджер в RHEL/CentOS.

Пример:

```
sudo yum install nginx
sudo yum update
sudo yum remove nginx
```

На современных системах чаще используется `dnf`.

Во многих дистрибутивах `yum` сейчас может быть просто совместимой обёрткой над `dnf`.

---

# `dnf`

`dnf` — современный пакетный менеджер в Fedora, RHEL, Rocky Linux, AlmaLinux, CentOS Stream.

Установить пакет:

```
sudo dnf install nginx
```

Обновить пакеты:

```
sudo dnf upgrade
```

или:

```
sudo dnf update
```

Удалить пакет:

```
sudo dnf remove nginx
```

Найти пакет:

```
dnf search nginx
```

Показать информацию о пакете:

```
dnf info nginx
```

Показать доступные версии:

```
dnf list --showduplicates nginx
```

# `rpm`

`rpm` — низкоуровневый менеджер `.rpm` пакетов.

Он похож по роли на `dpkg`, но для RHEL-based систем.

Установить локальный `.rpm` пакет:

```
sudo rpm -i package.rpm
```

Обновить локальный `.rpm` пакет:

```
sudo rpm -U package.rpm
```

Удалить пакет:

```
sudo rpm -e nginx
```

Показать установленные пакеты:

```
rpm -qa
```

Найти пакет:

```
rpm -qa | grep nginx
```

Показать, из какого пакета файл:

```
rpm -qf /usr/sbin/nginx
```

Показать файлы пакета:

```
rpm -ql nginx
```

Но в обычной работе лучше использовать `dnf`, потому что он сам решает зависимости.

# Как найти, из какого пакета файл

Это очень важный навык для DevOps/SRE.

Например, есть файл:

```
/usr/sbin/nginx
```

Нужно понять, какой пакет его установил.

В Debian/Ubuntu:

```
dpkg -S /usr/sbin/nginx
```

Пример вывода:

```
nginx-core: /usr/sbin/nginx
```

Значит файл принадлежит пакету `nginx-core`.

В RHEL/Rocky/Alma:

```
rpm -qf /usr/sbin/nginx
```

Пример:

```
nginx-1.24.0-1.el9.x86_64
```

Если файл ещё не установлен, но нужно найти, какой пакет его предоставляет:

Debian/Ubuntu:

```
sudo apt install apt-file
sudo apt-file update
apt-file search /usr/sbin/nginx
```

RHEL/Rocky/Alma:

```
dnf provides /usr/sbin/nginx
```

или:

```
dnf whatprovides /usr/sbin/nginx
```

# Как зафиксировать версию пакета

Иногда нужно запретить автоматическое обновление пакета.

Например, приложение работает только с конкретной версией `nginx`, `postgresql`, `docker`, `kubelet` и так далее.

## Debian/Ubuntu

Зафиксировать пакет:

```
sudo apt-mark hold nginx
```

Проверить зафиксированные пакеты:

```
apt-mark showhold
```

Снять фиксацию:

```
sudo apt-mark unhold nginx
```

Поставить конкретную версию:

```
sudo apt install nginx=1.24.0-2ubuntu7
```

Посмотреть доступные версии:

```
apt-cache policy nginx
```

или:

```
apt list -a nginx
```

---

## RHEL/Rocky/Alma/Fedora

Обычно используют plugin `versionlock`.

Установить:

```
sudo dnf install 'dnf-command(versionlock)'
```

Зафиксировать пакет:

```
sudo dnf versionlock add nginx
```

Показать lock-лист:

```
dnf versionlock list
```

Снять фиксацию:

```
sudo dnf versionlock delete nginx
```

Также можно временно исключить пакет из обновления:

```
sudo dnf upgrade --exclude=nginx
```

# Как обновлять сервер безопасно

Плохой вариант:

```
sudo apt update && sudo apt upgrade -y
```

на production-сервере без проверки.

Лучше так:

## 1. Посмотреть, что будет обновлено

Debian/Ubuntu:

```
sudo apt update
apt list --upgradable
```

RHEL/Rocky/Alma:

```
dnf check-update
```

---

## 2. Проверить важные пакеты

Особенно внимательно смотреть:

```
kernel
systemd
openssl
glibc
openssh-server
docker
containerd
kubelet
nginx
postgresql
mysql
redis
```

Почему?

Потому что обновление таких пакетов может:

- потребовать перезагрузку;
- перезапустить сервис;
- поменять поведение;
- сломать совместимость;
- обновить TLS/crypto-библиотеки;
- повлиять на контейнеры или Kubernetes node.

---

## 3. Сделать backup/snapshot

Перед важными обновлениями:

- snapshot VM;
- backup базы;
- backup конфигов;
- проверить restore-процедуру.

Минимально для конфигов:

```
sudo tar -czf etc-backup.tar.gz /etc
```

---

## 4. Обновлять сначала staging

Правильный порядок:

```
dev/staging → canary → production
```

Не стоит сначала обновлять самый важный production-сервер.

---

## 5. Обновлять по одному серверу

Если есть несколько серверов за балансировщиком:

```
server-1 обновили → проверили → вернули в балансировку
server-2 обновили → проверили → вернули в балансировку
server-3 обновили → проверили → вернули в балансировку
```

Такой подход называется rolling update.

---

## 6. Проверить сервисы после обновления

```
systemctl status nginx
systemctl status ssh
systemctl status docker
```

Посмотреть упавшие systemd units:

```
systemctl --failed
```

Посмотреть логи:

```
journalctl -p err -b
```

или для сервиса:

```
journalctl -u nginx -xe
```

---

## 7. Проверить, нужна ли перезагрузка

Debian/Ubuntu:

```
ls /var/run/reboot-required
```

Если файл есть — reboot нужен.

Также можно:

```
cat /var/run/reboot-required.pkgs
```

RHEL/Rocky/Alma:

```
sudo dnf install yum-utilsneeds-restarting -r
```

Если команда говорит, что reboot нужен — лучше запланировать перезагрузку.

# Security updates

Security updates — это обновления безопасности.

Они закрывают уязвимости в пакетах.

Например:

```
openssl
openssh
sudo
glibc
kernel
nginx
apache
curl
containerd
docker 
```

Для SRE важно понимать:

```
обычное обновление ≠ security update
```

Security update может быть критичным, потому что закрывает CVE.

CVE — это публичный идентификатор уязвимости.

Пример:

```
CVE-2024-3094
```

Типичные действия при security update:

1. понять, затронут ли сервер;
2. проверить версию уязвимого пакета;
3. обновить пакет;
4. перезапустить сервис;
5. если обновился kernel/glibc/systemd — возможно, reboot;
6. проверить, что сервис работает.

---

# Как обновить только security updates

## Debian/Ubuntu

Обычно security-обновления приходят из security-репозиториев.

Посмотреть доступные обновления:

```
apt list --upgradable
```

Поставить security updates можно через обычный upgrade, если настроены security-репозитории:

```
sudo apt update
sudo apt upgrade
```

Также часто используют:

```
unattended-upgrades
```

---

## RHEL/Rocky/Alma

Проверить security updates:

```
dnf updateinfo list security
```

Установить security updates:

```
sudo dnf upgrade --security
```

Посмотреть информацию:

```
dnf updateinfo
```

Посмотреть конкретную advisory:

```
dnf updateinfo info
```

# Unattended upgrades

`unattended-upgrades` — механизм автоматической установки обновлений безопасности на Debian/Ubuntu.

Установить:

```
sudo apt install unattended-upgrades
```

Включить:

```
sudo dpkg-reconfigure unattended-upgrades
```

Основные конфиги:

```
/etc/apt/apt.conf.d/50unattended-upgrades/etc/apt/apt.conf.d/20auto-upgrades
```

Пример `/etc/apt/apt.conf.d/20auto-upgrades`:

```
APT::Periodic::Update-Package-Lists "1";APT::Periodic::Unattended-Upgrade "1";
```

Это значит:

```
обновлять список пакетов каждый деньавтоматически ставить разрешённые обновления
```

Проверить логи:

```
cat /var/log/unattended-upgrades/unattended-upgrades.log
```

или:

```
ls /var/log/unattended-upgrades/
```

---

# Важный нюанс про unattended upgrades

Автообновления удобны, но на production надо быть осторожным.

Плюсы:

- быстро ставятся security patches;
- меньше риск забыть обновить сервер;
- хорошо для простых VM.

Минусы:

- пакет может обновиться неожиданно;
- сервис может перезапуститься;
- может понадобиться reboot;
- возможны несовместимости;
- сложнее контролировать change management.

Обычно нормальный подход:

```
критичные security updates — автоматизировать или быстро выкатывать
обычные feature updates — через плановое окно
сложные production-сервисы — обновлять контролируемо
```
